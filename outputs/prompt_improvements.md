Answer: You keep every change as a permanent record instead of just updating a row in a table because the full history of changes is valuable, especially in logistics. Rather than erasing or overwriting data, each correction or update is recorded as a new event, similar to how a ledger uses reversing entries instead of deleting lines. This event-sourced history captures the entire lifecycle of an entity—such as a load being posted, repriced, tendered, declined, booked, collected late, and delivered—which is essential for dispute resolution, penalty calculations, and performance analysis. Unlike conventional rows that only show the current state (e.g., that a load is delivered), event sourcing provides a provably consistent, detailed audit trail that can be reconstructed and verified at any time.

### Result

**The honest one — the cumulative jump did NOT prevent a hallucination here.** v1 was expected to drift on q05, whose context genuinely spans two documents and whose subject (event sourcing) is exactly the kind of thing a model knows independently. It did not drift: v1's answer is substantively grounded, and its specifics — posting a load, repricing, tendering, booking, delivery — track the corpus rather than invented detail. The real v1→v3 differences are attribution and discipline: v1 cites nothing, so a reader cannot verify a correct answer; v3 cites cqrs_chunk_008 and honours the five-sentence bound. Both versions correctly ignored the foreign migration chunk sitting in the same context. The finding is that a naive prompt is not reliably wrong — it is unreliably right, which is worse, because it means case-1's hallucination could not have been predicted from a single well-behaved sample. That is the argument for keeping all three prompts runnable rather than documenting them as prose.

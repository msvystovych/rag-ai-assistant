## Conclusion

Four routes, five step types and three tools run entirely offline, so this is the first homework whose committed artifact reproduces byte for byte — two consecutive `--examples` runs are identical files, and the test suite drives the shipped flow rather than a fake of it.

**State is load-bearing rather than decorative.** The booking route's third step cannot be reached except through its second, and the second is a verdict on the first's recorded observation. e3 and e4 put the same question with the same first observation and stop at different steps, which is the clearest evidence the rubric asks for: the workflow's behaviour changes because of what it already saw, not because of what it was asked.

**The interesting result is what a rule-based router cannot be talked into.** Homework #5 measured its model padding "carrier 817" into `CAR-00817` — well formed, real, and probably not the carrier the user meant; every syntactic validator accepted it and only the human gate stopped it. This router has no capacity to invent an operand: the same phrasing yields `missing_carrier_id`, and the malformed `FX-26-42` that Homework #5's model silently declined to emit is named here as a typo — the gain that homework's design doc predicted a pre-router would buy. Determinism buys refusals a helpful model will not make.

**Determinism does not buy correctness, and the router's real defects were all of one shape.** An adversarial review found three, and every one was the router selecting an operand the user had not offered. It bound a booking to the first identifier in the sentence, so "Where is load FX-A right now? Also, book a truck from carrier CAR-B." committed FX-A — an id that appears only in the read clause — while `check_authorisation` reported `ok: true`, because a gate verifies the operand it is handed. It counted only well-formed ids when checking for ambiguity, so "Book FX-A or FX-26-42 for CAR-B." discarded the user's own visible uncertainty and booked FX-A. And it read a well-formed `CAR-00817` as a mistyped identifier, because no rule consumed a carrier id on its own. The fixes are a booking route that resolves its operands only from the clause that asks for the booking, an ambiguity check that counts mistyped candidates too, and a gate refusal that prints both operands so a human can still catch the rest. **A confirmation gate is not a defence against a router that picked the wrong operand** — that is the lesson, and it generalises past this homework.

**The cost is on the other side and it is not small.** The router reads vocabulary and word position, never intent. "Commit semantics in the event log?" opens with a booking verb and is read as an imperative; a question naming a load is answered as a live lookup even when its verb phrase is definitional. Both are recorded in the design doc rather than patched, because a longer word list trades a rare miss for an unpredictable router. And the knowledge route is lexical BM25 over a rule-inferred filter — Homework #3's improved pipeline with its semantic half removed, because embedding a query needs the key this homework refuses to require. The answers it produces are extracted quotations with a chunk citation, not the synthesised, grounded paragraphs Homework #4 writes. On a documentation question Homework #4 is simply better, and it cannot run without a network. That is the trade this homework makes, and the reason it is worth stating is that the assignment's own § 2 invites it: routing without an LLM is normal here, and this is what normal costs.
